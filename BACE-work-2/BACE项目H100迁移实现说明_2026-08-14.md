# BACE 项目 H100 迁移实现说明

## 1. 迁移目标

将当前 `/home/naie/work/work-BACE` 的实际工作状态迁移为自包含目录 `/home/naie/work/work-BACE-2`。目标设备只需准备 NVIDIA Driver、conda 和 Python 包下载条件，即可完成环境安装、预检、smoke 和正式训练。

## 2. 实际迁移内容

迁移采用完整工作树复制，不依赖 `git clone`。这是必要的，因为源仓库基于 commit `14e5104a02d53b06cc3dbc3bc69d6707e8c19ade`，但 BACE collector、Replay、BatchERV Exact、测试和启动器包含大量未提交或未跟踪文件。

已复制：

- 完整 `.git`、tracked 修改和 untracked BACE 文件；
- `BACE-work`、`BACE-work-2`、`ICLR2027` 和顶层说明；
- 原 NPU、legacy、frontier、packed、Exact 和 WebShop 脚本；
- ALFWorld 数据与 Qwen2.5-1.5B-Instruct 模型；
- 16/64 ALFWorld placeholder parquet，消除目标机对 Geometry3K/Hugging Face cache 的启动依赖。

明确排除：

- `items_ins_v2.json.corrupt.partial`：186 MB，名称和内容状态均表明是未完成的损坏下载；
- `__pycache__`、`.pytest_cache`、`verl.egg-info`：可重建缓存；
- `outputs`、`tensorboard_log`：旧本地输出，不属于实现；
- Ascend conda 环境、torch_npu、HCCL 和 NPU 编译缓存：不能在 CUDA/H100 上复用。

## 3. GPU 运行层

新增通用启动器 `run_bace_alfworld_gpu.sh`，支持 1/2/4/8 GPU。它从 `CUDA_VISIBLE_DEVICES` 和 `GPU_COUNT` 解析卡数，验证 `ROLLOUT_TP`，使用 `trainer.device=cuda`，并清理继承的 Ascend/HCCL 环境变量。

smoke 与 full 脚本只是配置 wrapper，不复制 collector 实现。原 NPU 启动器全部保留，因此 CUDA 适配是新增可选路径。

当前 GPU 默认保持 BatchERV Exact 主方案：staged root generation、packed batching、`B=8`、`R_min=2`、BatchERV threshold 0.01、strict identity 和 occurrence credit。迁移没有把默认语义改成 valid-only。

## 4. 环境策略

没有复制 NPU conda 目录，而是固定可重建环境：Python 3.12、vLLM 0.11.0、FlashAttention 2.7.4.post1、torch/torchvision 2.8/0.23 系列、ALFWorld 0.4.2。版本来源以当前 upstream README 为主，避免混入旧 Dockerfile 中的 vLLM 0.6/0.8 栈。

二进制环境仍受目标机 Driver 和 CUDA ABI 约束，因此安装脚本必须在目标 H100 服务器执行。直接复制 NPU site-packages 既不能做到可复现，也无法加载 CUDA kernel。

## 5. 数据与可审计性

GPU 启动器延续 BACE artifact，并额外保存：环境、Git 状态和 diff、pip freeze、解析命令、Hydra override、GPU topology、训练前后 `nvidia-smi`，以及周期性显存/利用率/功耗/温度。

退出时自动运行 `recipe.bace_gigpo.validate_trace`。迁移目录还提供 SHA256 生成和校验脚本，用于传输后判断代码、文档、模型和 ALFWorld 数据是否损坏。

## 6. 尚需目标机现场确认的内容

- H100 数量与 80GB/94GB 型号；
- Driver 与 vLLM/PyTorch CUDA wheel 的兼容性；
- 单机 NVLink/NVSwitch/NCCL 拓扑；
- 实验输出最终存储路径；
- 是否有网络或内部 wheel mirror。

这些信息影响性能参数和安装来源，但不再要求修改 BACE 算法或复制固定卡数脚本。
