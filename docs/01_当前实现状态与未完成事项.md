## 3. 为什么 Slurm 显示 FAILED

Slurm job `3116958` 的状态为 `FAILED/1:0`，但日志顺序是：

1. 训练达到 150/150；
2. 最后一次 validation 完成；
3. 训练进程退出码为 0；
4. 作业尾部启动 `validate_trace.py`；
5. validator 读取一条超大 JSONL 时遇到 `JSONDecodeError: Unterminated string`，因此 wrapper 以 1 退出。

所以这是**训练后的验收程序失败**，不是模型训练失败。2026-08-26 使用当前代码重跑全量 validator，仍以同类 `JSONDecodeError` 退出；进一步逐文件检查至少确认 `step_00000001/leaves.jsonl` 第 1184 行是不完整 JSON（字符串在行尾被截断）。因此当前准确口径是：训练和 per-step finalize 完成，但这份长跑 artifacts **没有通过全量 trace 验收**。

旧的一次粗略“JSONL 完整性审计通过”结论已被这次可定位、可复现的解析失败推翻，不应继续引用。当前尚未统计全部坏行，也不能仅凭一条截断记录确定是写入中断、并发读取、共享存储或 artifact writer 的哪一层造成。修复 validator 不能恢复已经缺失的字段；如果需要发表级 trace 证明，应先保留原文件，再单独分析损坏范围，并用当前 HEAD 重新做 GPU 闭环。

## 7. 2026-08-29 至 08-30 的新增实现与审计

### Pairwise Exact acquisition

代码已在原 Full Exact 基础上新增：

- `pairwise.mode=full`：历史一轮冻结分配，仍是正式默认；
- `pairwise.mode=fixed`：每轮全局打包最多两个 branch，真实 outcome 后重新规划，不做 threshold stopping；
- `pairwise.mode=stopping`：按 residual capacity 执行 pair/single/stop，停止后的未用预算一次性转为 packed fallback natural roots，且不重新开启 branch。

CPU 专项已验证 `R+Q=B`、residual `L_max`、single branch、fallback、全局 round 记录和 trace 最终 topology。离线 A1 覆盖 2,400 个 task，其中 1,130 个 `Q>=3` task：45.58% 会在首 pair 后改变 allocation，但平均预期增益不足以支持替换 Full。threshold sensitivity 覆盖 4,520 个 task-threshold state，建议首轮只测试 `0.005`，再视结果测试 `0.0075`。

准确准入结论仍是 **HOLD / ABLATION ONLY**。C0 Full、C1 Fixed、C2 Stopping 的同 checkpoint H100 在线 smoke 尚未形成完成证据；不得把“代码已实现/CPU 测试通过”写成“在线效果已验证”。

### Credit decomposition 与 action-mean

A0 离线分解显示 BACE 的 local-credit 覆盖率提高，但中后期 local magnitude share 只增加约 1–2 个百分点，没有证据支持立即降低 `step_advantage_w` 或将主线切换为 `action_mean`。代码现支持 GiGPO/BACE 的 `occurrence|action_mean` 诊断，并为纯 GiGPO 捕获 action metadata；正式默认仍为 occurrence，A1/A2 action-mean 在线实验尚未完成。

### GiGPO fork 与 milestone checkpoint

新增从只读 BACE step-100 两卡 checkpoint 分叉 GiGPO 的 source validator、smoke/formal wrapper，以及 selected step 的 milestone 保存。milestone 使用同一文件系统内的硬链接和原子 rename：它使正常 checkpoint 轮转后仍能保留指定 step，但不会立即复制第二份多 GiB 数据。分叉验证与正式训练脚本存在不等于对应作业已完成。
