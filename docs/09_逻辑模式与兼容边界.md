# 逻辑模式与兼容边界

> 本文回答“代码里为什么有这么多模式，当前应该选哪个”。它也是 code review 时防止误接旧逻辑的检查表。

## 1. 当前推荐配置合同

新建 Exact BACE run 时，至少显式确认：

```text
algorithm.adv_estimator=bace_gigpo
algorithm.bace.enabled=true
algorithm.bace.variant=batch_erv_exact
algorithm.bace.topology=dynamic
algorithm.bace.dynamic_root_generation=staged
algorithm.bace.staged_root_batching=packed
algorithm.bace.branch_execution_mode=selected_worker
algorithm.bace.acquisition=batch_erv_exact
algorithm.bace.total_leaf_budget=8
algorithm.bace.min_natural_roots=2
algorithm.bace.max_branches_per_anchor=2
algorithm.bace.history_initial_mean=0.10
algorithm.bace.history_initial_strength=2.0
algorithm.bace.history_forgetting=0.8
algorithm.bace.batch_erv_threshold=0.005
algorithm.bace.invalid_action_mode=strict_identity
algorithm.bace.local_credit_mode=occurrence
algorithm.bace.tie_break_identity_mode=stable_v1   # 新 run 推荐
algorithm.gigpo.mode=mean_std_norm
algorithm.gigpo.step_advantage_w=1.0
algorithm.gamma=0.95
```

通用 launcher 已设置除 `stable_v1` 外的主线值。因为兼容旧 checkpoint，tie identity 仍建议由新 run 显式 override。

## 2. 模式矩阵

| 维度 | 可用值 | 当前主线 | 保留原因 |
|---|---|---|---|
| BACE enabled | false / true | true | false 走原始 collector，用于其他算法 |
| variant | legacy / batch_erv_exact | batch_erv_exact | legacy 保存早期 controller 和对照 |
| topology | fixed / dynamic | dynamic | fixed 是早期固定 R/B 方案 |
| root generation | preallocated / staged | staged | preallocated 会先生成完整候选池再筛 |
| staged batching | sequential / packed / frontier | packed | sequential 低效；frontier 是另一调度实验 |
| acquisition | random / erv / batch_erv_exact | batch_erv_exact | 旧 acquisition 用于历史实验 |
| branch executor | legacy_dense / selected_worker | selected_worker | dense 为对照和兼容 |
| invalid action | strict_identity / valid_only_branch / single_invalid_bucket | strict_identity | 其他模式用于消融 |
| local credit | occurrence / action_mean | occurrence | action_mean 是另一 credit 口径 |
| tie identity | legacy_uuid / stable_v1 | 新 run 用 stable_v1 | legacy_uuid 用于恢复旧 checkpoint |

## 3. 强制组合

collector 初始化会拒绝以下不合法组合：

- `batch_erv_exact` 不是 dynamic topology；
- `batch_erv_exact` 没有使用 staged generation；
- `batch_erv_exact` 没有使用 packed batching；
- `batch_erv_exact` 没有使用 `acquisition=batch_erv_exact`；
- `frontier` 没有搭配 dynamic + staged；
- selected-worker 所需的 env API 不存在。

因此 `frontier` 与当前 Exact variant 不能组合：Exact 强制 `packed`，frontier 是另一条实验逻辑。

## 4. 三组容易混淆的“legacy”

### `variant=legacy`

表示早期 BACE controller/acquisition 流程，可能使用 pilot/sequential ERV。它改变方法语义。

### `branch_execution_mode=legacy_dense`

表示 branch 的物理执行器。即使 acquisition 是 Exact，也可以理论上使用 dense executor；它主要改变执行成本与 worker 利用，不应改变冻结计划。

### `tie_break_identity_mode=legacy_uuid`

表示 tie 随机种子的身份来源。它保留旧 checkpoint 决策序列，但 UUID lineage 改变后不保证同一语义选择。

这三个字段相互独立，不能只看到“legacy”就认为是同一功能。

## 5. YAML 默认、launcher 和 checkpoint 的优先级

判断实际模式时采用以下顺序：

1. 当次 `resolved_command.sh` / Hydra resolved config；
2. artifact `manifest.json`；
3. checkpoint collector parameter signature；
4. launcher 脚本；
5. 最后才是 YAML default。

YAML default 服务于整个迁入框架，不是论文实验合同。修改 YAML default 还可能误伤其他入口，因此新实验优先在统一 launcher 中显式设置。

## 6. 可以只影响性能的参数

在数学 batch 不变且框架实现正确时，以下通常属于执行粒度：

- actor/log-prob micro batch；
- vLLM memory utilization；
- max batched tokens / max seqs；
- FSDP parameter/optimizer offload；
- eager mode；
- Ray CPU 数和每 env CPU；
- GPU 数、TP（但要重新确认全局 batch 和并行语义）。

这些参数仍需记录，因为可能触发数值或框架差异，但它们不应被用于改变 BACE 的 R/Q 或 acquisition 目标。

## 7. 会改变方法或实验可比性的参数

- leaf budget、min roots、max branches per anchor；
- competence prior、threshold、forgetting、transfer strength；
- Batch-ERV threshold 和 tie tolerance；
- topology/root generation/acquisition；
- invalid action mode 和 penalty；
- local credit mode、advantage normalization、gamma；
- group size、train task sampling、horizon；
- tie identity 和 random seed；
- 模型、数据、ALFWorld 版本。

改变这些字段应启动新 run；不要继续旧 dynamic BACE checkpoint。

## 8. 旧逻辑的处理原则

当前不删除旧逻辑，原因是：

- 需要读取或恢复已有 checkpoint；
- 需要做消融和 regression oracle；
- 某些环境/硬件入口仍引用旧字段；
- 保留问题演化证据。

但保留不代表推荐。新增代码必须：

1. 不让旧默认静默覆盖 Exact launcher；
2. 不在 Exact 路径中 fallback 到较小 branch batch；
3. 不让 reference/test-only Cartesian solver 进入正式路径；
4. 不让 branch outcome 污染 family history；
5. 不把 execution optimization 改成 acquisition replanning；
6. 不以兼容为由吞掉 checkpoint signature mismatch。

## 9. 入口脚本分类

### 当前可迁移入口

```text
examples/gigpo_trainer/run_bace_alfworld_gpu.sh
```

### 包装/示例入口

```text
run_bace_alfworld_gpu_smoke.sh
run_bace_alfworld_gpu_full.sh
run_bace_alfworld_h100_tiny_smoke.sh
```

使用前检查它们是否继续调用通用 launcher，并用 dry-run 查看最终 override。

### 历史或平台专用入口

- `examples/bace_gigpo/*.sbatch` 和 H100 rolling chain；
- 所有 `*_npu_*`；
- A100 transition wrappers；
- `frontier` 实验脚本；
- GiGPO reference/baseline 脚本。

这些文件不能作为当前 Exact 主线定义。

## 10. Resume 兼容边界

允许从旧 checkpoint 恢复的前提是：

- actor、optimizer、dataloader、global step 完整；
- `bace_collector_state.json` 存在且版本正确；
- collector parameter signature 一致；
- tie identity、history、topology、acquisition、credit 等状态相关参数不变；
- checkpoint tracker 指向完整目录。

如果要从 `legacy_uuid` 改成 `stable_v1`，或从 legacy variant 改成 Exact，应创建新 run。可以加载模型权重作为初始化，但不能称为同一训练 run 的无缝 resume。

## 11. Code review 检查表

- [ ] 变更实际走到当前 Exact 调用链，而不是只改旧类。
- [ ] `R+Q=B` 在 planning、capacity correction 和 artifact 中都成立。
- [ ] Exact request 数、顺序和 identity 在 chunking 前后不变。
- [ ] origin retry 只在同一 anchor/action 内替换未占用 origin，并完整记录 lineage。
- [ ] Replay prefix 不进入训练 batch。
- [ ] branch origin token/mask/log-prob 来自被冻结的 natural occurrence。
- [ ] branch failure 不被静默当作较小 batch 成功。
- [ ] family history 只吸收 natural root outcome。
- [ ] 新状态字段进入 checkpoint version/signature。
- [ ] 新 trace 字段由 validator 检查，写入失败不会假装 complete。
- [ ] 测试同时覆盖推荐路径和必要兼容路径。
- [ ] dry-run 的 resolved command 明确显示预期模式。
