# BACE 2×H100 正式训练与交接指南（2026-09-04）

本文档是当前 BACE ALFWorld 2×H100 实验的可执行交接说明。它说明当前三条可比实验的语义、实际入口、提交方式、恢复方式和验收位置。路径中的旧 `xsz96350` 实验目录是符号链接；真实结果存储在 `rwth2089` 的 HPCWORK 中，因此**不要复制模型、ALFWorld 或 parquet 数据**。

## 1. 当前状态与历史作业

下列三份 2026-09-02/03 的正式尝试不应作为完整实验结果继续使用：

| 作业 | 实验语义 | 到达位置 | 结论 |
| --- | --- | ---: | --- |
| `3447356` | C1，`R_min=2`，一次容量修正最多补 2 root | step 56 | 失败 |
| `3447359` | C0，`R_min=4`，一次容量修正最多补 1 root | step 150 | 训练完成，但训练后 trace 读取到损坏的旧 artifact JSONL，作业状态为失败；不可当作新的干净正式 run |
| `3447363` | C1，`R_min=4`，一次容量修正最多补 2 root | step 57 | 失败 |

`3447356` 和 `3447363` 的共同训练错误不是 CUDA、显卡或 PPO OOM：一次 `capacity_correction_batch_size=2` 将某任务的目标 root 数增加 2，但旧 collector 只生成第一个新增 slot。下一次 capacity assessment 因而观察到“已有 4 root、目标要求 5 root”而 fail-closed。

当前工作树已经修复该路径：`recipe/bace_gigpo/rollout_collector.py` 使用 `_pending_root_slots(...)` 收集从 `generated_by_task` 到新 `state.root_count` 的**全部连续缺失 slot**。例如目标从 2 增至 4，会同一 packed wave 生成 slot 2、3。它不改变叶子预算、Exact allocation、branch plan、PPO 样本语义或 replay 逻辑。

已在当前环境执行：

```bash
PYTHONPATH="$PWD" pytest -q \
  tests/bace_gigpo/test_batch_erv_exact.py \
  tests/bace_gigpo/test_root_wave_batching.py
```

结果为 `44 passed`。其中新增 root-wave 测试显式覆盖“一个任务由两 slot correction 后必须在同一 wave 收集两个缺失 root”的情况。

> Python 直接运行测试时需要 `PYTHONPATH="$PWD"`；否则当前 conda 环境会找不到仓库内的 `recipe.bace_gigpo` 包。这是测试启动路径问题，不是训练脚本问题（Slurm 的工作目录和运行方式正确）。

## 2. 三条实验的算法定义

三者共有的训练/环境参数：Qwen2.5-1.5B-Instruct、2×H100、TP=2、`B=8`、`L_max=2`、Exact Batch-ERV、dynamic/staged/packed roots、selected-worker replay、main-pool reuse、active-root executor、strict action identity、occurrence credit、stable tie-break、`tau=0.005`、seed 0、horizon 50、response length 512，以及 GiGPO reference 对齐的 PPO/rollout 参数。

| arm | `R_min` | correction batch | branch acquisition | 含义 |
| --- | ---: | ---: | --- | --- |
| C0-R4 | 4 | 1 | `pairwise.mode=full` | 一次冻结整批 Exact allocation；容量不足时每轮至多把 1 个 branch slot 转为 root slot。 |
| C1-R2 | 2 | 2 | `pairwise.mode=fixed`，每轮 2 branches | 先按滞后 family prior 生成 root；容量修正一次最多转 2 个 slot；之后每个 task 每轮执行 2 条 branch、更新局部 posterior 并重新分配下一对，直到完成冻结的 quota。`fixed` 不会因 `tau` 让结构剩余容量停止。 |
| C1-R4 | 4 | 2 | 与 C1-R2 相同 | 仅将最少自然 root 增至 4；因此每 task 的初始可分配 branch 上限从 6 变为 4。 |

`capacity_correction_batch_size=2` 的含义是“单次评估最多转换 2 个剩余 branch slot”，不是无条件额外生成 2 root。实际转换数为 `min(2, 当前 branch_count)`，并始终满足每任务 `R + Q = 8`。若补齐后的 root 仍无法提供足够 structural capacity，程序会继续评估并按同一规则再做下一轮 correction；不会伪造 branch，也不会越过 8 个 leaves。

## 4. 提交流程

### 4.1 先跑修复门禁

在提交三条新的正式 run 前，先确认当前排队中的一小时 C1 correction gate 已通过，或以新 run name 重提同样门禁。门禁必须至少完成一个 step，并检查 `summary.json`/trace 中的：

- `batch_erv_exact=1`、`staged_root_batching_packed=1`；
- selected-worker/main-pool reuse/active-root executor 均启用；
- `R+Q=8`；
- 出现强制 branch，且 trace `ok=true`；
- 当一次 correction 转换两个 slot 时，`capacity_correction_root_trajectories` 记录为 2，且无 root-count mismatch。

门禁只是验证修复，不自动提交正式作业。通过后才执行下面的 `sbatch` 命令。

### 4.2 提交新的、相互隔离的正式 run

以下命令选择 `c23g/rwth2082`，2 张 H100、32 CPU、244 GiB host memory。每一个 `BACE_RUN_NAME` 必须唯一；同一 run name 只能有一个活跃作业。

#### C0-R4（full Exact）

```bash
sbatch --job-name=c0-r4-corr1 \
  --export=ALL,BACE_RUN_NAME=c0_r4_corr1_full150_s0_20260904,BACE_SEED=0,\
BACE_SCHEDULING_PROFILE=optimized,MIN_NATURAL_ROOTS=4,\
CAPACITY_CORRECTION_BATCH_SIZE=1,MILESTONE_CHECKPOINT_STEPS=none \
  examples/bace_gigpo/run_alfworld_h100_2gpu_reference_aligned.sbatch
```

`MILESTONE_CHECKPOINT_STEPS=none` 是刻意指定的：该 C0 脚本原本的默认值会把 step 10/75/100/140 永久复制到 `preserved_checkpoints/`。这与当前“仅保留最近 1–2 份可恢复 checkpoint”的存储策略不符。

#### C1-R2（fixed pairwise，每轮两 branch）

```bash
sbatch --time=23:30:00 --job-name=c1-r2-corr2 \
  --export=ALL,PAIRWISE_ARM=c1,PAIRWISE_PHASE=full,\
BACE_RUN_NAME=c1_r2_corr2_full150_s0_20260904,MIN_NATURAL_ROOTS=2,\
CAPACITY_CORRECTION_BATCH_SIZE=2,HISTORY_INITIAL_MEAN=0.10,\
HISTORY_INITIAL_STRENGTH=2.0 \
  examples/bace_gigpo/slurm_pairwise_online_smoke_2gpu.sbatch
```

#### C1-R4（fixed pairwise，每轮两 branch）

```bash
sbatch --time=23:30:00 --job-name=c1-r4-corr2 \
  --export=ALL,PAIRWISE_ARM=c1,PAIRWISE_PHASE=full,\
BACE_RUN_NAME=c1_r4_corr2_full150_s0_20260904,MIN_NATURAL_ROOTS=4,\
CAPACITY_CORRECTION_BATCH_SIZE=2,HISTORY_INITIAL_MEAN=0.10,\
HISTORY_INITIAL_STRENGTH=2.0 \
  examples/bace_gigpo/slurm_pairwise_online_smoke_2gpu.sbatch
```

注意 C1 脚本自身的 `#SBATCH --time=01:00:00` 是 gate/smoke 默认值。因此 C1 的正式提交必须显式带 `--time=23:30:00`，如上所示。C0 脚本自身已经是 `23:30:00`。

### 4.3 中断或到达时限后的恢复

三种正式 run 都是自动恢复而不是固定 20/40/… segment：

1. 保存频率为每 5 step；常规 checkpoint 目录只保留最近 2 份完整 checkpoint。
2. 新 allocation 使用**完全相同**的 arm、run name、`R_min`、correction batch、seed、model 和 target step=150 重提同一命令。
3. 启动前脚本会先识别磁盘上旧进程留下的 checkpoint 并轮转；随后 `trainer.resume_mode=auto` 从本 run 最新完整 checkpoint 恢复。
4. 禁止以 C0 checkpoint 恢复 C1，禁止在 C1-R2 与 C1-R4 之间互相恢复；BACE state signature 会拒绝这类语义不同的恢复。

请勿在一个作业尚运行时再提交相同 `BACE_RUN_NAME`，否则两个进程会竞争相同的 artifact/checkpoint 文件。

## 6. 不应混淆的两类历史失败

1. **C1 step 56/57 root-count mismatch**：已由当前 collector 修复并被单测覆盖；新正式 run 必须从 step 0 使用新代码，不能恢复旧 C1 checkpoint。
2. **旧 C0 作业训练后 trace JSONL 解析失败**：发生在训练达到 step 150 之后，不能证明新的 trace 写入/验证链已经通过。因此新 C0 run 仍需执行完整最终 trace 验收，不能只因旧作业训练完成就跳过。

## 7. 当前代码变更的最小边界

本轮修复只改变 Exact packed collector 在容量修正后的 root-slot 物化：由“每 deficient task 只取当前第一个 slot”改为“每 deficient task 取直到新目标的所有连续缺失 slot”。原实现保留在 Git 历史/diff 中；未删除任何旧算法路径。它不改变 C0/C1 的定义，也不改变 branch acquisition、replay prefix restoration 或 learner/PPO credit 的含义。
