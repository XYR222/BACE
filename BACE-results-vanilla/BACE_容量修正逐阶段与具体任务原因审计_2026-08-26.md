# BACE 容量修正逐阶段与具体任务原因审计

日期：2026-08-26
实验：`bace_alfworld_qwen2_5_1_5b_exact_rotation_fix_seed0`
范围：正式 4×H100，训练 step 1–150
口径：本文把日志中的 `training_step` 称为训练 step；用户所说的 epoch 在本实验中按同一训练进度编号理解。每 10 个训练 step 为一段。

## 1. 结论先行

容量修正是必要的安全机制，而且本次没有破坏训练语义：

- 2,400 个 task 实例共初始规划 7,116 个 branch；
- 最终执行 5,703 个 branch；
- 1,413 个 branch slot 被改为 natural root，即补充生成 1,413 条 root；
- 361 个 task 至少发生过一次修正，覆盖 77/150 个训练 step；
- 每个 task 最终都满足 `R + Q = 8`；
- 没有 root 被丢弃，branch 请求均通过验证；
- Exact、packed、selected-worker 和 Replay 链路均保持有效。

这里的“补充 root”不是无效样本：这些轨迹成为最终 topology 的 natural root，进入 PPO 数据，并用于 natural-root family history 更新。真正的问题是，很多 root 在初始 branch quota 已经规划后才被追加生成，导致额外的 wave、同步和环境 rollout 时间。

## 2. 当前实现检查的规则

正式配置为：

```text
total_leaf_budget = 8
min_natural_roots = 2
max_branches_per_anchor = 2
batch_erv_threshold = 0.005
```

对每个 task，系统需要满足以下规则：

1. **终端预算规则**：`R + Q = 8`。
2. **最少 root 规则**：初始规划至少保留 2 条 natural root。
3. **anchor 容量规则**：每个 structural anchor 最多提供 2 个 branch slot。
4. **Exact capacity 规则**：最终 `Q` 不能超过所有 anchor 的 information capacity 总和 `C`。
5. **Batch-ERV 阈值规则**：一个 anchor 的第 1/第 2 个 branch 只有在其边际 ERV 大于或等于 `0.005`（含设定的 tie tolerance）时，才计入 capacity。
6. **结构 anchor 规则**：anchor 至少要有两个已观测 action；只有一个 action 的前缀不能形成可比较的 Batch-ERV branch anchor。

如果第 4 条不满足，当前实现每轮把一个 branch slot 转成一个 root slot：

```text
R <- R + 1
Q <- Q - 1
```

然后重新计算 anchor 和 capacity，直到 `C >= Q`，或者 `Q=0`。因此修正是单向、保守、可验证的。

## 3. 为什么初始 branch 规划会偏乐观

代码路径：

- `recipe/bace_gigpo/topology.py:305-324`：根据 lagged family history 初始化 quota；
- `recipe/bace_gigpo/topology.py:326-377`：root 生成后计算真实 capacity 并修正；
- `recipe/bace_gigpo/rollout_collector.py:1048-1158`：Exact packed root 生成和追加 correction wave。

当前时序是：

```text
上一 step 的 family history
        -> family readiness
        -> 初始 Q_plan/R_plan
        -> 生成 R_plan 条 root
        -> 从真实 root 构建 anchor/action posterior
        -> 计算 Exact information capacity C
        -> 若 C<Q，则补 root 并减少 Q
```

`Q_plan` 由 family competence readiness 决定，不能提前知道当前 task 的真实 anchor 结构。只有 root 真正跑完后，系统才知道：

- 是否出现相同前缀但不同 action 的结构 anchor；
- 每个 anchor 有几个 action；
- 当前 action posterior 是否仍有足够不确定性；
- 第 1、2 个 branch 的边际 ERV 是否超过 `0.005`。

所以“family 很有能力”与“当前 task 适合做很多 branch”不是同一个量。前者是跨 step 的 family 统计，后者是当前 task 的局部信息价值。

### 4.1 初次 capacity 不满足的原因分类

分类使用每个 task 初次 capacity 检查时的结构：令 `A` 为 structural anchor 数，`C` 为 information capacity，`Q_plan` 为 family plan 给出的初始 branch quota。由于 `max_branches_per_anchor=2`，`2A` 是结构 anchor 可以提供的理论上限。

| 初始原因 | 判定 | task 数 | 被转换的 branch slot |
|---|---|---:|---:|
| 无 structural anchor | `A=0`，没有可比较的双 action 前缀 | 67 | 337 |
| 结构 anchor 上限不足 | `A>0` 且 `2A < Q_plan` | 180 | 700 |
| ERV 边际不足 | `2A >= Q_plan` 但 `C < Q_plan` | 114 | 376 |
| 合计 | 发生至少一次修正 | **361** | **1,413** |

前两类合计 247 个 task、1,037 个 slot，占全部修正 slot 的 73.4%。这表示主要问题是当前 root 数量下的可比较 anchor 结构不足或过少；另外 26.6% 是结构 anchor 数量原则上够，但部分 branch 的边际 ERV 不足。

注意：`2A < Q_plan` 是必要的结构上限判断，不代表每个 anchor 都一定能贡献 2 个 branch；实际 ERV 低时容量只会更小。因此“结构上限不足”是结构性主因，可能同时包含 ERV 低的影响。

## 7. 重点案例的逐轮解释

### 7.1 step 58：结构 anchor 足够，但 ERV 不够

task `pick/place:b1cd64e7`：

```text
初始规划：R=3, Q=5
首次评估：A=5，anchor capacity=[0,0,0,1,2]，C=3
```

虽然有 5 个 structural anchor，理论上限 `2A=10` 大于 `Q=5`，但只有 3 个 branch slot 的边际 ERV 达到阈值。因此先把一个 slot 改成 root。追加后又发现当前 capacity 变化，最终：

```text
check 0: R=4,Q=4,C=3
check 1: R=5,Q=3,C=2
check 2: R=5,Q=3,C=5
```

最终补 2 条 root，保留 3 条 branch。该例是典型的“不是 anchor 数量不够，而是 marginal ERV 不能支持当前 Q”。

### 7.2 step 69：anchor 数量形成硬上限

task `pick/place:b253711d`：

```text
初始规划：R=3,Q=5
首次评估：A=1，capacity=[2]，C=2
```

即使这个唯一 anchor 能达到最大 2 个 branch，`2A=2` 仍小于 `Q=5`，因此至少必须把 3 个 branch slot 变成 root。实际追加过程中 capacity 还会波动：

```text
check 0: R=4,Q=4,C=2
check 1: R=5,Q=3,C=3
check 2: R=6,Q=2,C=1
check 3: R=7,Q=1,C=0
check 4: R=8,Q=0,C=0
```

最终补 5 条 root，Q 降为 0。它说明少量 root 的前缀多样性不足，即使其中存在一个可用 anchor，也无法支撑高 branch quota。

### 7.3 step 81：完全没有 anchor

task `pick/place:516881d6`：

```text
初始规划：R=2,Q=6
首次评估：A=0，C=0
```

这表示当前 2 条 root 没有产生任何“相同前缀、至少两个不同 action”的 structural anchor。追加 root 后一度出现 1 个 anchor，但其 capacity 又降为 0；最终只保留 Q=2，补 4 条 root。该情况不是 vLLM、Replay 或 GPU 问题，而是当前 root 样本没有提供可用于 action credit 比较的结构。

### 7.4 step 96：anchor 数量原则上够，但边际 ERV 不足

task `pick/place:2a74f9a6`：

```text
初始规划：R=2,Q=6
首次评估：A=3，capacity=[1,2,2]，C=5
```

`2A=6`，结构上限足以承载 6 个 branch，但实际容量只有 5。追加 root 后 capacity 反而在某轮降到 1，最后只剩 Q=1。原因是部分 anchor 的第 2 个边际 ERV 没有达到 `0.005`，不是缺少结构 anchor 本身。

### 7.5 step 136：后期最严重的混合情况

step 136 全 step 统计：

```text
初始规划 Q=96，最终 Q=47，补 root=49，correction wave=6
```

一个 clean task (`705f7fc7`) 的首次状态是 `A=1,C=0`，其唯一 anchor capacity 为 0，既无法形成足够的结构容量，也没有通过 ERV 阈值的 branch。另一个 pick/place task (`661d99d5`) 有 6 个 anchor，但 capacity 全为 0：

```text
anchor capacities=[0,0,0,0,0,0]
```

这说明“anchor 数很多”仍不代表可以执行 branch；anchor 内部的 action posterior 可能已经不产生足够的边际信息价值。

step 136 的耗时为：

| 阶段 | 耗时 |
|---|---:|
| 初始 planned root | 84.74 秒 |
| capacity correction root | **329.09 秒** |
| branch suffix | 181.96 秒 |
| Replay 验证 | 19.72 秒 |
| 总 step | 657.89 秒 |

因此该 step 的主要拖慢因素是追加 root wave，而不是 branch replay。

### 7.6 直接查看 ERV 阈值的例子

对每个 anchor，`delta_1` 是第一个 branch 的边际 ERV，`delta_2` 是在已有一个 branch 后再增加第二个 branch 的边际 ERV。只有满足 `delta >= 0.005` 的连续 slot 才计入该 anchor capacity。

| step / task | structural anchor A | 各 anchor capacity | `delta_1` 通过数 | `delta_2` 通过数 | C | 解释 |
|---|---:|---|---:|---:|---:|---|
| 58 / `b1cd64e7` | 5 | `[0,0,0,1,2]` | 2/5 | 1/5 | 3 | 只有少数 action 对比的边际 ERV 超过阈值 |
| 96 / `2a74f9a6` | 3 | `[1,2,2]` | 3/3 | 2/3 | 5 | 第一个 branch 基本有价值，但一个第二 branch 不够有价值 |
| 136 / `661d99d5` | 6 | `[0,0,0,0,0,0]` | 0/6 | 0/6 | 0 | 有 structural anchor，但所有边际 ERV 都低于 0.005 |
| 141 / `2342d883` | 2 | `[1,1]` | 2/2 | 0/2 | 2 | 每个 anchor 只能支持 1 个 branch，第二个 slot 的 ERV 不足 |

对应的实际数值进一步说明差别：

- step 58 的 `delta_1` 通过值约为 `0.006945、0.061343`，只有一个 `delta_2≈0.005008` 刚刚通过；
- step 96 的三个 `delta_1` 约为 `0.006901、0.011779、0.022012`，但一个 `delta_2≈0.004000` 低于阈值；
- step 136 的全部 `delta_1` 最大约 `0.004467`，已经低于 `0.005`，因此 capacity 为 0；
- step 141 的两个 `delta_1≈0.006080` 通过，但两个 `delta_2≈0.003466` 不通过，所以 capacity 只有 2 而不是 4。

这就是“ERV 过小”的准确含义：不是 ERV 计算失败，而是当前 posterior 下继续采样的预期信息增益没有达到设定阈值。

## 9. 对当前情况的建议

### 9.1 必须保留的部分

不建议删除或绕过：

- capacity correction；
- Exact 全局 allocation；
- packed root generation；
- selected-worker branch execution；
- occurrence-level PPO credit；
- branch Replay validation。

删除 correction 会让最终 branch quota 可能超过真实 capacity，导致无法生成合法 ERV request，或者被迫静默丢弃 branch，破坏 `R+Q=8` 和 PPO 数据语义。

### 9.2 最低风险改进：先补诊断

当前日志已经能回答“修正了多少”，但还没有直接记录第一次检查的完整原因。建议增加：

- `initial_planned_branch_count`；
- `initial_information_capacity`；
- `structural_anchor_count`；
- 每个 anchor 的 action 数；
- 每个 anchor 的 `delta_by_size` 和 capacity；
- 原因标签：`no_structural_anchor`、`anchor_ceiling`、`erv_below_threshold`；
- 每一轮 `R/Q/C/A`；
- 每个 family 的 correction root 秒数和 wave straggler。

这不会改变算法，可先确认究竟是 root 多样性不足还是 ERV 已经过小。

### 9.3 推荐的算法方向：lagged capacity-aware quota

保留“不读取当前 batch outcome 决定初始 topology”的原则，同时利用之前 step 的 family 统计预测一个保守容量：

```text
C_hat = family-level lagged capacity estimate
Q_plan = min(round(6 * readiness), conservative_quantile(C_hat))
R_plan = 8 - Q_plan
```

然后继续保留现有 correction 作为安全网。优先对现有 150-step trace 做离线 replay，比较不同预测方法能否减少 correction，而不改变 branch ERV 和 PPO 语义。

### 9.4 执行层优化

在不改变最终 topology 的情况下：

- 继续使用 deficient-task packed correction wave；
- 对 root 环境步数做长度分桶，降低长轨迹拖尾；
- 减少每轮 reset、concat 和调度开销；
- 记录纯 rollout 时间与等待时间；
- 继续监测 active compaction 和 padding。

本次 branch suffix active/dense 比约 37.5%，compaction 已避免约 62.5% 的 dense inactive 执行；不能为了修正 root 问题回退这一逻辑。

### 9.5 不建议直接采用

- 直接把 `Q_plan` 全部强制执行；
- 降低 `batch_erv_threshold` 只为减少 correction；
- 一次把所有 deficit slot 都转换成 root；
- 提高 `R_min` 后不重新做方法对照；
- 把 correction root 排除在 PPO 或 family history 之外。

这些做法可能减少报表中的修正，却会改变方法或掩盖 capacity 不满足的事实。

## 10. 验收标准

后续若优化 quota 或 correction 执行，至少重新确认：

- 每 task 最终 `R+Q=8`；
- `Q <= information_capacity`；
- 每个 branch request 均被 Replay 验证或明确失败终止；
- branch outcome 不进入 family history；
- Exact、packed、selected-worker 标志保持为 1；
- `discarded_roots=0`；
- trace validation 通过；
- correction ratio、correction wave 和 step p95 不恶化；
- validation 与 branch success 不出现回退。

当前 150-step run 可作为基线：

```text
correction ratio        = 19.86%
correction root time    = 2.37 h
correction time fraction= 13.71%
```

工程优化目标可以暂定为 correction ratio <10%、修正时间占比 <5%，但这不是牺牲 ERV 质量和训练结果的硬指标。

统计方法：

1. 从 `family_topology_plans.jsonl` 读取未修正的 `Q_plan/R_plan`；
2. 从该 step 的首条 `capacity_checks.jsonl` 读取第一次实际 anchor design 的 `A/C`；
3. 以 `max_branches_per_anchor=2` 判断 `2A<Q_plan` 的结构上限；
4. 以 `C<Q_plan` 判断 Exact capacity 不满足；
5. 从最终 capacity record 读取 `correction_count`；
6. 按 step 和 family 汇总，并用 TensorBoard scalar 汇总中的 correction wave/time 字段核对总数。
