# WebShop 共享搜索与会话打包实现及五阶段验证

日期：2026-08-08

## 1. 问题结论

原始 GiGPO WebShop 配置创建 128 个训练逻辑环境和 128 个验证逻辑环境。原实现中每个 Ray actor 都导入 Pyserini 并启动独立 JVM，因此出现 JVM native thread 和内存耗尽。

第一版共享搜索将 JVM 数量限制为 16，但真实 `128+128` 环境测试又发现 256 个独立 Python/Ray 进程会触发 Ray 内存保护。因此最终方案同时处理两层重复资源：

1. 256 个逻辑环境共享 16 个 Lucene/JVM 搜索 actors。
2. 每 8 个逻辑环境由一个 packed Ray actor 承载，训练和验证共 32 个物理会话 actors。

逻辑环境数量、训练 batch、group size、验证数量、session 状态、动作、奖励和 GiGPO 更新均未减少。

## 2. 可选模式与兼容性

原始逻辑没有删除。默认配置为：

```yaml
env:
  webshop:
    search_backend: local
    sessions_per_actor: 1
```

该模式仍是一会话 actor 对应一个本地 LuceneSearcher。NPU 训练脚本显式启用：

```yaml
search_backend: ray_shared
search_pool_size: 16
sessions_per_actor: 8
```

因此 upstream 行为和本方案可以通过配置切换。

## 3. 主要实现

### 3.1 延迟启动 JVM

将 `LuceneSearcher` 从模块顶层导入移动到 `init_search_engine()` 内部。普通会话 actor 在共享模式下不会因导入 WebShop 模块而启动 JVM。

### 3.2 共享 Lucene 搜索池

新增 `WebshopSearchWorker`，每个搜索 actor 持有一个 LuceneSearcher，并仅返回可序列化的 ASIN 列表。`RayLuceneSearchClient` 保持 WebShop 原有同步搜索接口。

训练环境和验证环境复用同一搜索池。查询按逻辑 worker 编号取模分配到搜索 shard。

### 3.3 Packed 会话 actor

新增 `PackedWebshopWorker`，在一个 Ray 进程中托管多个独立 `WebAgentTextEnv`。reset、step、replay 和 render 按逻辑 slot 分组调用，再恢复为原始逻辑顺序。

每个 slot 仍持有独立 WebShop session、浏览状态、动作历史和 reward 状态。默认 `sessions_per_actor=1` 不进入该路径。

### 3.4 资源和诊断

训练脚本设置受控 JVM 参数，并记录 JVM、线程、RSS、搜索次数、错误数和拓扑。主要运行文件包括：

- `search_pool_ready.json`
- `train_topology.json`
- `validation_topology.json`
- `train_search_final.json`
- 单卡训练的 `run_metadata.txt`、NPU 快照、rollout JSONL 和 BACE trace

## 4. 五阶段验证结果

### 阶段一：Local 与 Shared 搜索一致性

16 条固定 query 的前 50 个 ASIN及顺序完全一致。

报告：`BACE-work/experiment_traces/webshop_shared_search/search_parity.json`

结果：通过。

### 阶段二：128 并发搜索压力

配置为 16 个搜索 actors、128 并发、20 轮，共 2560 次搜索。

- 搜索错误：0
- 平均单请求耗时：0.0226 秒
- p95：0.0440 秒
- p99：0.0927 秒
- 第一轮冷态 batch：0.6801 秒
- 第 20 轮热态 batch：0.1722 秒

报告：`BACE-work/experiment_traces/webshop_shared_search/search_stress_pool16_128c_20r.json`

结果：通过。

### 阶段三：128 训练加 128 验证真实环境

第一次仅共享 JVM、仍创建 256 个 Python actors 的方案在约 150 个 actor 时触发 Ray OOM，证明只共享搜索不足。

启用 `sessions_per_actor=8` 后：

- 训练逻辑环境：128
- 验证逻辑环境：128
- 物理会话 actors：16 + 16
- 搜索 actors/JVM：16
- train reset：128/128
- validation reset：128/128
- train 并发 search：128/128
- validation 并发 search：128/128
- 搜索错误：0

报告：`BACE-work/experiment_traces/webshop_shared_search/environment_stress_128train_128val_pool16_packed8.json`

结果：通过。

### 阶段四：环境语义回归

对 session 500、501、502 比较原始 local 单会话与 packed+shared 模式：

- 商品 click 后 observation
- reward 和 done
- replay 恢复结果

所有字段逐项一致。

报告：`BACE-work/experiment_traces/webshop_shared_search/semantic_parity_local_vs_packed_shared.json`

## 5. 当前边界与后续风险

1. 当前节点只有一个可见 NPU，因此尚未执行 8 卡短跑或完整 150 epoch 训练。
2. `search_pool_size=16` 已通过压力测试，但仍应在实际 8 卡节点记录搜索等待占比，再比较 8、16、32。
3. packed 模式共享进程级 Python 随机状态。标准 WebShop search/click/replay 已证明一致；若实验使用 `<r>` 等随机控制搜索动作，需要增加专门的 RNG 隔离测试。
4. 当前固定协议为 `use_small=true`。全量 1.18M 商品配置还需要共享商品 catalog，不能直接按当前内存结论外推。
5. Gym 0.24 和部分 WebShop 依赖会输出弃用警告，但本轮未造成行为错误。

## 6. 下一步

在 8 卡节点使用 `examples/gigpo_trainer/run_webshop_npu_8card_train.sh` 进行原始并发短跑。脚本默认仍为 8 卡、16 搜索 actors、每 actor 8 会话，并保存 checkpoint、TensorBoard、rollout、validation 和 WebShop runtime 诊断。
