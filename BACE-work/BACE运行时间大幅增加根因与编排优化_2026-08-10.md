## 1. 结论

BACE 的主要耗时不是 Replay、ERV 后验计算或 trace 落盘，而是 dynamic topology 的 staged root 编排把互不依赖的 natural root 轨迹拆成了多个小 rollout wave。模型 token 数减少并不等于 wall-clock 减少：vLLM/NPU 更依赖每次请求的 batch 宽度，多个小 wave 会带来 kernel、Ray、环境 step 和调度空转。

已有 50 epoch trace 的统计如下：

| 指标 | GiGPO 原版 | BACE staged | 结论 |
|---|---:|---:|---|
| 总 wall time（50 step） | 约 16.68 h | 约 26.49 h | BACE 慢约 59% |
| 平均 `timing_s/gen` | 504.45 s | 1544.45 s | root/branch generation 是主瓶颈 |
| 平均 `timing_s/step` | 1225.45 s | 1942.80 s | 单 step 慢约 717 s |
| 平均 throughput | 272.68 | 89.02 | BACE 约低 67% |
| mean total tokens | 2.651 M | 1.375 M | BACE 少约 48%，但没有转化为时间收益 |
| Replay trace 累计 | - | 149.03 s / 50 step | 平均约 3 s/step，不是主因 |

BACE 50 step 中：

- `generated_roots_mean = final_roots_mean = 3.911`；
- `discarded_roots_mean = 0`；
- `planned_branches_mean = final_branches_mean = 0.08875`；
- 18 个 step 没有 branch，32 个 step 有 ERV branch；
- 所有 71 个 requested branch 都通过 strict identity Replay 验证。

这说明算法数据层没有回到 preallocation 的“生成后丢弃”问题，当前问题是编排层吞吐：约 4 条 root 被拆成多次约 16 条输入的生成调用。

需要强调：该 GiGPO/BACE 对照适合定位工程瓶颈，但还不是最终公平的方法对比。GiGPO 使用 `rollout.n=8`，当前 BACE 使用 `total_leaf_budget=4`；后续效果与效率结论必须分别做 equal-budget（4 对 4）和 original-scale（8 对 8）实验。

## 2. 当前训练编排

一次 BACE training step 的调用顺序是：

```text
RayPPOTrainer
  -> BaceTrajectoryCollector.multi_turn_loop
       -> staged natural roots
            -> pilot roots
            -> competence posterior / readiness
            -> planned root/branch quota
            -> completion roots
            -> capacity correction
       -> immutable root event logs
       -> AnchorIndex
       -> ERV coordinator
       -> initial anchor Replay validation
       -> origin transition validation
       -> branch suffix generation
       -> root + branch origin + suffix concat
  -> reward / old log-prob / reference log-prob
  -> BACE advantage
  -> diagnostic artifact write
  -> actor update
```

原 staged collector 的 root 部分近似是：

```text
for pilot slot:
    collect(all tasks)       # pilot_roots=2 时调用 2 次
compute posterior
while some task needs another root:
    collect(one slot per needed task)
    concat all previous DataProto
    rebuild all root event logs
while capacity is deficient:
    collect(one corrective slot per deficient task)
    concat all previous DataProto
```

在 `train_data_size=16, total_leaf_budget=4, pilot_roots=2` 下，低 competence step 常见序列为：

```text
16 条 pilot root wave 0
16 条 pilot root wave 1
16 条 completion root wave 2
16 条 completion root wave 3
```

GiGPO 则一次以更宽的 group rollout batch 生成 trajectories。BACE 虽然最终 token 少，但每个生成调用的 batch 过窄，NPU 利用率和 vLLM batching 效率都更差。

## 3. 代码层根因

### 3.1 Pilot wave 串行

pilot outcome 必须先于 competence posterior，但 pilot 的不同 slot 之间没有模型参数依赖。旧代码通过两次 `collect(task_indices)` 串行生成 pilot。若直接把两次请求合并，又会丢失“同 task 使用同一个 concrete reset key”的身份约束，因此需要先解决 reset-key 获取问题。

### 3.2 Completion wave 逐 slot 补齐

posterior 计算后，每个 task 的目标 root 数已经确定。旧代码每轮只补一个 slot，导致所有 task 都需要两条 completion root 时仍发出两次小 batch。此阶段没有先后依赖，应一次发送全部已知缺口。

### 3.3 重复 concat 和重复解析

每增加一批 root，旧代码都会重新 `_concat_batches(root_batches)`，并多次 `build_root_event_logs(root_output)`。这会复制 token tensor、object metadata，并重新扫描已完成的全部事件。它不是 NPU 主瓶颈，但会随 root 数量和 token 长度增加而放大 CPU/内存压力。

### 3.4 Branch suffix 是次要瓶颈

每个 ERV round 的 suffix 通常只有 1 到 6 条请求，属于小 batch 生成。已有 trace 中 branch-active step 比无 branch step 的 `timing_s/gen` 平均高约 86 s，但贡献明显小于 root wave 拆分。

### 3.5 Replay 和 artifact 不是首要目标

Replay 累计 149.03 s，平均约 3 s/step；artifact 写入虽产生约 3.3 GB trace，但 `timing_s/adv` 约 4 到 5 s/step。它们应继续保留关键调试数据，不应为了追求吞吐删除 strict identity 或审计字段。

### 3.6 Done trajectory 仍参与生成

通用 `vanilla_multi_turn_loop` 每一轮先为 wave 内全部 rows 调用 `generate_sequences`，再用 `active_masks` 丢弃已经 done 的 rows；只有整个 wave 全部 done 才停止。BACE 50 step 的平均 episode length 为 36.69/40，说明这部分不是首要的 3 倍耗时来源，但确实存在“已支付生成计算、未计入最终训练 token”的浪费。branch suffix loop 也有同类全 batch 生成问题。

这一项不能只通过过滤 tensor rows 修正，因为环境管理器的 `active_worker_indices`、memory、observation、request 和 lineage 必须同步压缩并在输出时恢复映射。它应作为 packed root 验证后的第二阶段工程优化。

## 4. 已实现的低风险优化

新增配置：

```yaml
algorithm.bace.staged_root_batching: sequential  # 原兼容路径
# packed                                        # 新优化路径
```

### 4.1 Packed root schedule

`packed` 路径位于 `recipe/bace_gigpo/rollout_collector.py`，原 `sequential` 路径完整保留。新路径执行：

```text
1. reset-key probe：只 reset 每个 task 的 slot 0，读取 game file/session id
2. packed pilot wave：绑定同一个 reset key，一次生成 pilot_roots 个 slot
3. posterior / initial quota
4. packed completion wave：一次发送所有已知缺失的 root slots
5. capacity correction：每轮只对 deficient task 增加一个 root，保持依赖正确
6. 最终只 concat 一次，并只构建一次增量 root logs
```

reset-key probe 不调用模型，只增加一次环境 reset；它保证 packed pilot 仍满足：

```text
same task -> same concrete game/session
worker index = task_index * total_leaf_budget + root_slot
R + Q = B
```

因此不能把 packed 理解成跨 task 或跨 session 混合环境；它只是把身份已经冻结、彼此独立的 task-slot 放到同一个模型 batch。

### 4.2 增量日志和一次性合并

packed 路径在每个 wave 完成时只解析该 wave 的 `RootEventLog`，保留 Python log list；planner 只使用 logs，最终 topology 确定后才执行一次 `_concat_batches`。这避免了旧路径反复复制完整 DataProto。

### 4.3 细粒度指标

每个 BACE step 的 `bace/*` 指标现在额外记录：

```text
root_reset_key_probe_seconds
pilot_root_waves / pilot_root_trajectories / pilot_root_generation_seconds
completion_root_waves / completion_root_trajectories / completion_root_generation_seconds
capacity_correction_waves / capacity_correction_trajectories / capacity_correction_generation_seconds
root_generation_waves
root_event_logging_seconds
root_batch_concat_seconds
training_batch_concat_seconds
capacity_planning_seconds
branch_suffix_waves / branch_suffix_trajectories / branch_suffix_generation_seconds
replay_validation_seconds
artifact_write_seconds
staged_root_batching_packed  # 1=packed, 0=sequential
```

这样可以直接比较优化前后的 wall-clock，而不需要从总 `timing_s/gen` 推断。

### 4.4 训练脚本

`examples/bace_gigpo/run_alfworld_npu_8card_50epoch.sh` 已显式启用：

```text
algorithm.bace.dynamic_root_generation=staged
algorithm.bace.staged_root_batching=packed
```

原有 `preallocated` 和 `staged + sequential` 仍可通过 override 运行，未删除任何原逻辑。

## 5. 预期收益和边界

在当前 trace 的 `final_roots_mean≈3.91`、`pilot_roots=2` 条件下，packed 路径通常会把 root generation call 从约 4 次降为：

```text
1 次 packed pilot + 1 次 packed completion
```

若 capacity correction 触发，再加实际需要的 correction waves。由于当前 50 step 中 `planned_branches == final_branches`，预计多数 step 不需要 correction wave。

不能事先承诺总 wall-clock 按 wave 数线性下降，因为：

- packed batch 会变宽，单 wave 可能占用更多峰值显存；
- environment reset-key probe 有固定开销；
- branch suffix、old log-prob、reference log-prob 和 actor update 不会因 root packing 自动消失；
- vLLM/NPU 对真实 prompt 长度分布的 batching 效果需要真实 smoke 验证。

若 packed root 后仍明显慢于 GiGPO，后续优先级为：

1. active-only multi-turn generation：不再为已 done rows 调用模型，同时保留原 fixed-shape 路径作为开关；
2. 同一 ERV round 内按 remaining horizon 对 branch suffix 分桶并批量执行；
3. 将 artifact token arrays 改为可选异步/分块写入，但继续同步保存 action identity、anchor、reward、lineage 和 Replay 结果；
4. 再评估是否需要改变 `pilot_roots`、leaf budget 等方法参数，避免先用语义变化掩盖工程瓶颈。

## 6. 验证要求

优化路径必须完成以下检查后才适合长训练：

1. 单元测试：slot packing、worker mapping、reset-key 绑定、capacity correction、`R+Q=B`；
2. 1-step 单卡 fake/ALFWorld smoke：检查 `packed` 指标和 artifact summary；
3. 3 到 5 step 单卡性能对比：`preallocated`、`staged+sequential`、`staged+packed`；
4. 8 卡短跑：确认显存不超过原成功脚本，确认 `bace/validated <= bace/requested`；
5. 冻结相同 parquet、seed、模型 commit、保存策略后，再比较 GiGPO/BACE；
6. 长训练中保留 `roots.jsonl`、`anchors.jsonl`、`topology.jsonl`、`replay_attempts.jsonl` 和 `trainable_occurrences.jsonl`，性能实验可以关闭 token arrays，但不得关闭 identity/reward/lineage 字段。

## 7. 当前判断

优化前，BACE 的算法逻辑基本正确，但 orchestration 尚未达到高吞吐实现。首要工作是验证 packed root schedule 的真实 NPU wall-clock；在此之前不能宣称 BACE 相对 GiGPO 有性能优势。若 packed 后 generation 仍占主导，再按新增指标定位是 vLLM batch、branch suffix 还是环境/Ray 调度问题，而不是继续修改 Replay 语义。
