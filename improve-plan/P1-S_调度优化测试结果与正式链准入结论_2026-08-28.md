## 1. 摘要结论

本轮 P1-S 调度优化已经完成代码实现、CPU 专项回归、H100 S0/S1/S2/S3 对比、三步稳定性训练，以及一次真实 4-rank FSDP 外部 checkpoint 隔离门禁。

当前结论如下：

1. **S1：main ALFWorld worker pool 复用有效。**
   - 在相同 56 个 branch 请求下，capacity cohorts 从 4 降至 1；
   - branch suffix generation 从 159.81 秒降至 54.68 秒，减少 65.78%；
   - 单步端到端时间从 396.84 秒降至 270.70 秒，减少 31.79%。

2. **S2：active-root executor 有明确正收益。**
   - 单个正式规模 profile 避免了 1,614 个 inactive root rows；
   - root generation 从 84.10 秒降至 74.63 秒，减少 11.27%；
   - 单步端到端时间从 396.84 秒降至 369.02 秒，减少约 7.01%。

3. **S3：S1+S2 组合是当前自动选择结果。**
   - branch capacity cohorts 为 1；
   - 避免 1,614 个 inactive root rows；
   - 单步端到端时间为 282.66 秒，相比 S0 减少约 28.78%；
   - 三个连续 stability steps 全部训练完成，trace 均为 `ok=true`。

4. **外部 resume checkpoint 被误删的问题已经在真实 4-rank FSDP 流程中确认修复。**
   - 门禁作业 `3263870` 从外部 step 148 恢复并保存 step 149；
   - 使用最严格的 `MAX_CHECKPOINTS=1`；
   - 保存后源 checkpoint 文件清单完全不变；
   - 新 checkpoint 的 actor、optimizer、scheduler/RNG、dataloader、BACE state 和 tracker 全部完整。

5. **算法和调度逻辑已经具备进入正式链的条件，但当前正式脚本不能原样提交。**
   - 当前 Hydra 默认仍为 `branch_pool_mode=dedicated`、`root_active_executor=false`；
   - 当前 4 卡 rolling 脚本默认仍为 `MAX_CHECKPOINTS=1`；
   - 正式提交前必须显式切换到 S3、固定 micro-batch 16，并保留最近两份 checkpoint。

6. **性能结果具有明显工程意义，但尚不能宣称严格统计学显著。**
   - S1 的结构性证据很强，因为 S0/S1 请求数相同且 cohorts 明确从 4 降为 1；
   - S2/S3 目前只有一次随机 rollout A/B，没有重复试验和置信区间；
   - 因此报告应使用“工程上显著”或“代表性 profile 明确正收益”，不应写成统计显著性结论。

## 2. 优化范围与算法不变量

本轮只修改系统调度，不修改 BACE-GiGPO 方法定义。保留的不变量包括：

```text
Exact Batch-ERV global allocation
dynamic staged root generation
packed root barrier
capacity correction
frozen root backbone
ReplayRequest identity and validation
strict action identity
occurrence-level credit
GiGPO-compatible advantage
unified PPO training semantics
R + Q = 8
```

新增且可独立开关的调度项为：

```text
S1: algorithm.bace.branch_pool_mode=main_reuse
S2: algorithm.bace.root_active_executor=true
S3: S1 + S2
```

旧逻辑没有删除：

```text
branch_pool_mode=dedicated
root_active_executor=false
```

因此旧路径仍可作为 correctness fallback 和 A/B baseline。

### 5.2 相对收益

#### S1 相对 S0

```text

```

这是当前最强的对照证据，因为 S0 与 S1 的 branch 请求数均为 56，root active executor 均关闭，差异集中在 branch physical scheduling。

#### S2 相对 S0

```text
root generation reduction = 11.27%
end-to-end step reduction ≈ 7.01%
inactive root rows avoided = 1,614
```

S2 确认 done roots 已从后续 model submission 中消失。但真实随机 rollout 下 S0 与 S2 的最终 branch 数不同，因此端到端时间不能视作严格 token-for-token 配对结果。

#### S3 相对 S0

```text
branch suffix reduction = 58.89%
root generation reduction = 11.36%
end-to-end step reduction ≈ 28.78%
capacity cohorts = 1
inactive root rows avoided = 1,614
```

自动选择器要求：

```text
minimum root gain = 2%
pair regression tolerance = 5%
fallback = S1
```

S3 达到选择阈值，最终 `selected_mode=s3`。

### 5.3 对随机性的解释

S0/S1 的 branch 请求均为 56，而 S2/S3 为 45。这不是 branch 丢失：

- active compaction 改变了 physical batching 和随机采样执行顺序；
- stochastic vLLM rollout 不要求不同 physical scheduling 下逐 token 一致；
- correctness 判断依赖 deterministic/mock tests、logical identity、Replay validation 和 trace，而不是随机 rollout 的 token-by-token 一致。

因此：

- S1 的性能收益是强对照证据；
- S2/S3 的结果是代表性工程 profile；
- 若要发表统计显著性结论，需要从同一 checkpoint 做多次独立重复并报告均值、标准差和置信区间。

## 7. Checkpoint 修复设计与验证边界

### 7.1 已修复的问题

FSDP manager 现在在轮转前按目标 checkpoint root 过滤 `previous_saved_paths`：

```text
source/root-A/global_step_148/actor
target/root-B/global_step_149/actor

root-A != root-B
→ source 不进入 target 的轮转集合
```

同时轮转从“写新 actor 前”移到了 actor shards 写完并完成 rank barrier 之后。

### 7.2 已验证的实际行为

门禁 `3263870` 使用 `MAX_CHECKPOINTS=1`，仍满足：

- source before/after manifest 完全一致；
- target 4-rank model shards 完整；
- target 4-rank optimizer shards 完整；
- target 4-rank extra state 完整；
- target `data.pt` 完整；
- target `bace_collector_state.json.global_step=149`；
- target tracker 为 149；
- target trace `ok=true`。

### 7.3 仍应采用两份 checkpoint 的原因

当前 actor manager 在 actor shards 保存成功后执行 actor 轮转，controller 随后才写：

```text
data.pt
bace_collector_state.json
latest_checkpointed_iteration.txt
```

如果 controller-side 状态写盘失败，tracker 不会前移，这是正确的；但在 `MAX_CHECKPOINTS=1` 下，同一输出 root 的上一份 actor 可能已经被轮转。

因此正式链应使用：

```text
MAX_CHECKPOINTS=2
SAVE_FREQ=5
```

当前实验盘预检约有 2 TiB 空余，保留两份 checkpoint 没有容量压力。两份保留策略可以保证一次不完整的新保存不会破坏最后一份完整可恢复 checkpoint。

## 9. 性能结论的推荐表述

### 9.1 可以使用的表述

> 在相同 late checkpoint 和正式规模 workload 下，main-pool branch reuse 将 56 个 branch 请求的 capacity cohorts 从 4 降至 1，branch suffix generation 时间减少 65.8%，单步端到端时间减少 31.8%。Active-root executor 在代表性 late-step profile 中避免了 1,614 个 inactive root submissions，并将 root generation 时间减少约 11.3%。组合 S3 在该 profile 中将端到端 step 时间减少约 28.8%，并通过连续三步稳定性和 4-rank checkpoint 门禁。

### 9.2 不应使用的表述

当前不能写：

> S3 在统计学上显著加速 28.8%。

原因是：

- 目前每种配置只有一次正式规模随机 profile；
- S0/S1 与 S2/S3 的随机 rollout branch 数不同；
- 尚未计算方差、置信区间或显著性检验。

### 9.3 如需论文级统计结论

建议在相同 checkpoint 上做至少 3–5 次独立重复，记录：

```text
step wall-clock
root generation wall-clock
branch suffix wall-clock
branch request count
generated token count
root rows avoided
padding rows
GPU utilization
```

按 token 数、branch 数和 root logical turns 做归一化，并报告均值、标准差与 95% 置信区间。

这不是进入正式训练的必要条件，但属于发表严格性能结论的必要补充。
