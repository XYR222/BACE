# P1-A：Rmin=4 与初始 2-root 容量修正对比分析

日期：2026-08-28  
基线文档：`BACE-results-vanilla/BACE_初始2Root任务容量修正分类统计_2026-08-27.md`  
当前诊断作业：Slurm `3253029`，C 路径 `bace_exact_quota_rmin4_from148_migration_diag_seed0_3253029`

## 1. 结论摘要

将最少 natural root 从 2 提高到 4 后，容量修正没有消失，但修正的性质发生了变化：

> Rmin=4 缓解了“初始 root 太少导致 structural anchor 不足”的问题，但无法解决“已有 anchor 的边际 ERV 不足”问题。

当前 step149–150 的诊断样本中：

- 初始 `R=4` 的 task instance 有 23 个；
- 其中 13 个发生容量修正，task 修正率为 **56.5%**；
- 初始 branch slot 为 92 个，其中 50 个被转成补充 root，slot 修正率为 **54.3%**；
- 发生修正的 task 平均最终为 **7.85 条 root**；
- 13 个修正 task 中，12 个最终达到 8-root，1 个达到 6-root；
- `pick-and-place` 仍然是主要问题来源，当前小样本修正率为 **88.9%**；
- 修正原因中，ERV 低于阈值与 structural 原因各占约一半，另有一个 task 在后续复查时出现 capacity 下降。

这说明 Rmin=4 是合理的低风险改进，但不能被理解为容量修正问题的根治方案。

## 3. 配额变化

旧配置和当前配置的预算分别为：

```text
旧：R=2, Q=8-2=6
当前：R=4, Q=8-4=4
```

每次容量修正仍然执行：

```text
R <- R + 1
Q <- Q - 1
```

总约束始终保持：

```text
R + Q = 8
```

Rmin=4 的直接效果是：初始多生成 2 条 root，初始最多请求的 branch 从 6 降低到 4；但若这 4 个 branch 仍没有足够 capacity，系统仍会继续补 root，直到 capacity 收敛或达到 R=8。

## 5. 与旧初始 2-root 基线对比

| 指标 | 旧：初始 R=2 | 当前 C：初始 R=4 | 解释 |
|---|---:|---:|---|
| 初始 branch quota | 6 | 4 | Rmin=4 预先分配更多 root |
| task 修正率 | 60.32% | 56.5% | 当前小样本略低，不能外推 |
| slot 修正率 | 42.20% | 54.3% | 当前样本中剩余 4 个 slot 更容易全部被转 root |
| 修正后平均最终 root | 6.20 | 7.85 | 当前修正 task 更集中地补到 8-root |
| 修正后中位数 | 7 | 8 | 与上项一致 |
| 修正后众数 | 8 | 8 | 两者均常见补满 root |

### 5.1 为什么 task 修正率略降，但最终 root 反而更高

旧 R=2 时，task 一开始有 6 个 branch slot，capacity 可能支持其中一部分，因此最终可能停在 R=3、4、5、6 或 7。

当前 R=4 时，task 一开始只有 4 个 branch slot：如果 capacity 不足，最多只需把这 4 个 slot 转换成 root；若四个 slot 都不满足，task 就会直接到 R=8。因此 Rmin=4 降低了初始 branch 风险，但使“发生修正时直接到 8-root”的分布更加集中。

## 6. 按 task family 分类

当前仅统计初始 R=4 的 task：

| Family | 初始 R=4 | 发生修正 | task 修正率 | 补充 root | 主要最终 root |
|---|---:|---:|---:|---:|---|
| pick-and-place | 9 | 8 | **88.9%** | 32 | 8 |
| clean-then-place | 5 | 1 | 20.0% | 4 | 8 |
| cool-then-place | 2 | 2 | 100% | 6 | 6、8 |
| heat-then-place | 4 | 0 | 0% | 0 | — |
| look-at-object-in-light | 3 | 2 | 66.7% | 8 | 8 |
| pick-two-and-place | 0 | 0 | — | 0 | — |
| **合计** | **23** | **13** | **56.5%** | **50** | — |

### 6.1 pick-and-place 仍是主要瓶颈

旧基线中，pick-and-place 初始 R=2 的修正率为 71.26%。当前 Rmin=4 的 step149–150 小样本中，初始 R=4 的修正率仍为 88.9%。

这表明问题不只是初始 root 数量不足，而是：

1. 该 family 的 readiness 较高，初始 branch quota 容易被规划到较高水平；
2. root 数量增加后，新增 root 不一定产生新的 structural anchor；
3. 已存在的 anchor 中，新增 action 的 ERV 经常低于 `0.005`；
4. 因此 branch quota 即使从 6 降至 4，仍可能无法满足。

不能把这一结果解释为 Rmin=4 失败，而应解释为 pick-and-place 具有独立的 family-level capacity 特征。

## 7. 当前容量修正原因

对 13 个发生修正的 task，使用首次 capacity 检查中的 `initial_structural_anchor_count`、`initial_information_capacity` 和 `initial_quota_deficit` 分类：

| 原因 | 判定逻辑 | task 数 | 占修正 task |
|---|---|---:|---:|
| 无 structural anchor | `A=0` | 2 | 15.4% |
| structural anchor 上限不足 | `A>0` 且 `2A<Q` | 4 | 30.8% |
| ERV 边际容量不足 | 结构上限够但 `C<Q` | 6 | 46.2% |
| 后续复查时 capacity 下降 | 首次 `C>=Q`，后续仍需修正 | 1 | 7.7% |
| **合计** | — | **13** | **100%** |

### 7.1 与旧基线的原因结构对比

旧初始 R=2 基线：无 anchor 20.07%，structural ceiling 48.36%，ERV 边际不足 31.58%，结构类合计 68.4%。

当前 Rmin=4：无 anchor 15.4%，structural ceiling 30.8%，ERV 边际不足 46.2%，后续动态复查 7.7%，结构类合计 46.2%。方向上符合预期：增加最少 root 后，结构性不足下降，ERV 不足相对突出。但当前样本只有 13 个修正 task，不能据此断言真实长期比例已经发生同样幅度的变化。

### 7.2 无 structural anchor

这类 task 的 root 没有形成可比较的共同前缀：

```text
同一 anchor 前缀
    + 至少两个不同 action
    -> 才能构造 local action posterior
    -> 才能产生 structural branch capacity
```

Rmin=4 后，这类问题比例下降，但没有完全消失，因为额外 root 可能仍访问不同前缀，未必形成重复 anchor。

### 7.3 structural anchor 上限不足

即使 anchor 存在，每个 anchor 最多支持 2 个 branch。若：

```text
2A < Q
```

那么结构上限本身就不足以承载当前 quota。Rmin=4 将 Q 从 6 降到 4，因此这类问题有所缓解，但当有效 anchor 很少时仍会发生。

### 7.4 ERV 边际容量不足

这是当前最常见的单一原因。anchor 已经存在，但新增 branch 的预期信息价值不超过阈值：

```text
delta_1 < 0.005
```

或第二个 branch 的边际增益过低：

```text
delta_2 < 0.005
```

这通常意味着 action posterior 已经比较确定，或不同 action 的成功率差异不足。它不是 ERV 计算崩溃，也不是 Replay 请求非法。

### 7.5 后续复查时 capacity 下降

step150 的一个 cool-then-place task 首次 capacity 检查时 `C=Q=2`，但在追加 root 和后续复查后仍出现修正，最终从 R=4 变为 R=6。这说明 capacity 会随新增 root、posterior 更新或 anchor 重算而变化，当前 trace 已将该情况显式记录。

## 8. 这是否证明 Rmin=4 有效

### 已证明

1. Rmin=4 能正常运行，不破坏 Exact Batch-ERV、packed root、selected-worker 或 Replay。
2. `R+Q=8` 约束始终成立。
3. 初始 branch quota 从 6 降到 4，当前样本中的结构类容量不足下降。
4. 发生修正时，系统能安全将 branch slot 转成 root，不产生非法 branch request。
5. trace 能记录首次 capacity、每轮修正、最终 root/branch 和动态复查结果。

### 尚未证明

1. 不能证明 Rmin=4 会提高最终模型成功率。
2. 不能用两个 step 判断长期 correction rate。
3. 不能证明 ERV threshold `0.005` 对所有 family 都合适。
4. 不能证明 pick-and-place 的高修正率仅靠提高 Rmin 就能解决。

## 9. 当前建议

### 9.1 必须保留的安全机制

- Exact Batch-ERV capacity check；
- capacity correction；
- `R+Q=8` 约束；
- packed root generation；
- selected-worker branch execution；
- Replay validation；
- occurrence-level PPO credit。

不能为了降低修正率而强制执行所有预规划 branch，否则会产生超过真实 capacity 的非法请求。

### 9.2 优先进行的低风险分析

在正式训练中继续记录每个 task 的 `R_plan`、`Q_plan`、首次和每轮 `A/C`、每个 anchor 的 action 数量、`delta_1/delta_2`、原因标签、每轮 `R/Q/C/A`、family-level correction rate、wave 次数和耗时。

### 9.3 后续算法方向

在不改变 Exact 安全网的前提下，可以引入 family-level 的滞后、保守 quota 预测：

```text
C_hat = lagged family capacity estimate
Q_plan = min(round(4 * readiness), conservative_capacity_quantile(C_hat))
R_plan = 8 - Q_plan
```

建议先对已有完整 150-step trace 做离线回放，比较不同预测方式能否降低 correction rate，再进行新的小规模 A/B profile。暂时不建议仅凭两个 step 调整 ERV threshold。

## 10. 最终判断

> **Rmin=4 是合理的保守 quota 改进。它减少了由初始 root 数量不足引起的 structural capacity 问题，但当前主要瓶颈已经暴露为局部 ERV 不足，尤其集中在 pick-and-place。容量修正仍然是必要且正确的安全网；下一步应优化 family-level quota 预测，而不是取消 correction 或强制执行 branch。**
