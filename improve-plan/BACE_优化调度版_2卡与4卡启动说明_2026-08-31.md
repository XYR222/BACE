# BACE 优化调度版：2 卡与 4 卡 H100 启动说明

本文说明当前用于 ALFWorld、Qwen2.5-1.5B-Instruct 的两套 BACE 正式入口：

- 2×H100：`examples/bace_gigpo/run_alfworld_h100_2gpu_reference_aligned.sbatch`
- 4×H100：`examples/bace_gigpo/run_alfworld_h100_4gpu_rolling.sbatch`

两套入口均使用 P1-S 调度优化的最终组合：branch 使用主 rollout worker 池（`main_reuse`），root rollout 使用 active compaction（`root_active_executor=true`）。这只改变 rollout/replay 的执行调度与无效行压缩；Exact 全局 Batch-ERV 分配、packed root、selected-worker branch 执行、PPO 数据语义和 GiGPO-compatible advantage 均保持不变。

## 2. 优化调度配置的含义

两卡入口通过 `BACE_SCHEDULING_PROFILE` 切换：

| profile | branch worker 池 | root 执行 | 用途 |
|---|---|---|---|
| `legacy` | `dedicated` | `false` | 旧实现对照 |
| `optimized` | `main_reuse` | `true` | 当前正式优化版 |

4 卡 rolling 入口固定使用优化组合，不提供 legacy 开关：

```text
algorithm.bace.branch_pool_mode=main_reuse
algorithm.bace.root_active_executor=true
```

两者共同保持的 BACE 主方法参数包括：

```text
variant=batch_erv_exact
topology=dynamic
dynamic_root_generation=staged
staged_root_batching=packed
branch_execution_mode=selected_worker
total_leaf_budget=8
min_natural_roots=2
max_branches_per_anchor=2
history_initial_mean=0.10
history_initial_strength=2.0
history_forgetting=0.8
batch_erv_threshold=0.005
local_credit_mode=occurrence
invalid_action_mode=strict_identity
```

这里的 Exact 意味着每个 task 最终满足 `R + Q = 8`，而不是 pilot wave 或近似分配。`selected_worker` 意味着 branch suffix 只由其选中的 worker 继续执行；前缀 replay 仅用于验证 origin transition，不会再次进行执行恢复 replay。

## 3. 2×H100 优化版

### 3.1 资源与训练参数

2 卡入口的 Slurm 默认资源为 `c23g / rwth2082 / 2×H100 / 32 CPU / 244 GiB / 23:30:00`。除 BACE 自身参数外，训练相关配置与 `AFH/examples/gigpo_trainer/run_alfworld.sh` 对齐：

```text
train/val batch              = 16 / 128
group size                   = 8
horizon / response length    = 50 / 512
learning rate                = 1e-6
PPO mini-batch               = 256
actor/logprob micro-batch    = 32 / 32
rollout tensor parallelism   = 2
vLLM max batched tokens      = 8192
vLLM max sequences           = 1024
gamma / KL coefficient       = 0.95 / 0.01
validation frequency         = 5
total steps                  = 150
```

运行时会取消 `VLLM_ATTENTION_BACKEND`，让当前 H100/vLLM 栈自动选择可工作的 FlashAttention 后端；这不是算法超参数变更。

### 3.2 提交一个新 seed 的正式作业

下面示例提交 seed 1。`BACE_RUN_NAME` 必须唯一；同一 run name 会触发自动恢复，而不是重新从 0 开始。

```bash
cd /hpcwork/xsz96350/fu_project/work-BACE/verl-agent-src

sbatch --parsable \
  --export=ALL,BACE_SCHEDULING_PROFILE=optimized,BACE_SEED=1,\
BACE_RUN_NAME=bace_alfworld_qwen2_5_1_5b_exact_2gpu_s3_seed1_YYYYMMDD,\
TARGET_STEP=150,SAVE_FREQ=5,MAX_CHECKPOINTS=2,\
MILESTONE_CHECKPOINT_STEPS=none \
  examples/bace_gigpo/run_alfworld_h100_2gpu_reference_aligned.sbatch
```

seed 2 只需把 `BACE_SEED=2` 和 run name 中的 `seed1` 同时替换为 `seed2`。当前已提交的实例为：

| seed | run name | Slurm job | 2026-08-31 审计状态 |
|---:|---|---:|---|
| 1 | `bace_alfworld_qwen2_5_1_5b_exact_2gpu_s3_seed1_20260831` | `3351657` | `PENDING (Priority)` |
| 2 | `bace_alfworld_qwen2_5_1_5b_exact_2gpu_s3_seed2_20260831` | `3351658` | `PENDING (Priority)` |

### 3.3 2 卡 checkpoint 策略

常规多 seed 实验应使用：

```text
SAVE_FREQ=5
MAX_CHECKPOINTS=2
MILESTONE_CHECKPOINT_STEPS=none
```

含义是每 5 step 保存一次，完成后只保留最新两份可恢复 checkpoint；没有额外永久保存点。`none` 会完全移除 Hydra 的 `trainer.milestone_checkpoint_steps` 和 `trainer.milestone_checkpoint_dir` 参数，而不仅仅是不触发某个空目录。

若确实需要 seed 0 的长期审计保留点，2 卡入口的默认值是 `10,75,100,140`。不要把逗号列表直接放在 `sbatch --export=...` 中，因为 Slurm 会把逗号视为环境变量分隔符。应先在 shell 中导出：

```bash
export MILESTONE_CHECKPOINT_STEPS=10,75,100,140
sbatch --export=ALL,BACE_SCHEDULING_PROFILE=optimized,BACE_SEED=0,\
BACE_RUN_NAME=my_2gpu_seed0,TARGET_STEP=150,SAVE_FREQ=5,MAX_CHECKPOINTS=2 \
  examples/bace_gigpo/run_alfworld_h100_2gpu_reference_aligned.sbatch
unset MILESTONE_CHECKPOINT_STEPS
```

## 4. 4×H100 优化版

### 4.1 资源与训练参数

4 卡入口使用 `c23g / rwth2082 / 4×H100 / 64 CPU / 325 GiB / 23:30:00`。尽管脚本头部保留了历史 `c25g` 默认，正式提交命令显式覆盖到经验证的 `c23g/rwth2082`。

与 2 卡版相比，4 卡正式入口的主要资源差异是：

```text
GPU_COUNT                   = 4（必须显式传入）
actor/logprob micro-batch   = 16 / 16
rollout tensor parallelism  = 1
vLLM max batched tokens     = 16384
vLLM max sequences          = 128
```

其余核心训练参数为 train/val `16/128`、group `8`、horizon `50`、response `512`、LR `1e-6`、PPO mini-batch `256`、KL `0.01`、gamma `0.95`、validation 每 5 step、总计 150 step。

### 4.2 提交一个新 seed 的正式作业

下面示例提交 seed 1。`GPU_COUNT=4` 不能省略：通用训练入口据此构建四卡 FSDP/vLLM 配置。

```bash

sbatch --parsable \
  --partition=c23g --account=rwth2082 \
  --export=ALL,GPU_COUNT=4,BACE_SEED=1,\
BACE_RUN_NAME=bace_alfworld_qwen2_5_1_5b_exact_p1s_s3_seed1_YYYYMMDD,\
TARGET_STEP=150,ACTOR_MICRO_BATCH=16,MAX_CHECKPOINTS=2,SAVE_FREQ=5,\
MILESTONE_CHECKPOINT_STEPS=none \
  examples/bace_gigpo/run_alfworld_h100_4gpu_rolling.sbatch
```

seed 2 将 `BACE_SEED=2` 与 run name 中的 `seed1` 改为 `seed2`。当前已提交的实例为：

|---:|---|---:|---|
| 1 | `bace_alfworld_qwen2_5_1_5b_exact_p1s_s3_seed1_20260831` | `3351882` | `PENDING (Priority)` |
| 2 | `bace_alfworld_qwen2_5_1_5b_exact_p1s_s3_seed2_20260831` | `3351883` | `PENDING (Priority)` |

### 4.3 4 卡 checkpoint 策略与续跑

旧 4 卡 seed 0 优化 run 保留 `10,75,140` 作为长期恢复点。新的多 seed run 使用 `MILESTONE_CHECKPOINT_STEPS=none`，只保留普通轮转 checkpoint，原因是四个新增 run（2 卡 seed 1/2、4 卡 seed 1/2）同时保留全部长期 snapshot 会显著增加磁盘风险。

rolling 入口采用：

```text
trainer.resume_mode=auto
SAVE_FREQ=5
MAX_CHECKPOINTS=2
```

若作业因墙钟时间或节点故障中断，使用**完全相同的** `BACE_RUN_NAME`、`BACE_SEED`、资源和保存策略再次提交即可。启动时会读取 `latest_checkpointed_iteration.txt`，先识别/清理上一进程留下的旧 checkpoint，再从最近完成保存的 step 恢复。不要为了续跑改 run name，也不要手动把 checkpoint 复制到新目录。

## 5. 启动前 dry-run

dry-run 会加载环境、检查路径、写入解析命令与 metadata，但不会执行 rollout 或产生 checkpoint。两个 wrapper 都会先执行 GPU preflight，因此应在相应卡数的 allocation/计算节点内运行；直接在无 GPU 的登录节点执行会按设计失败。建议每次更改 run name、seed、保存策略或资源参数后执行一次。

### 2 卡 dry-run

```bash
cd /hpcwork/xsz96350/fu_project/work-BACE/verl-agent-src
DRY_RUN=1 BACE_SCHEDULING_PROFILE=optimized BACE_SEED=1 \
BACE_RUN_NAME=dryrun_2gpu_seed1 MILESTONE_CHECKPOINT_STEPS=none \
bash examples/bace_gigpo/run_alfworld_h100_2gpu_reference_aligned.sbatch
```

检查生成的命令：

```bash
rg 'env.seed=|branch_pool_mode=|root_active_executor=|save_freq=|max_actor_ckpt_to_keep=|milestone_checkpoint' \
  /hpcwork/xsz96350/fu_project/work-BACE/experiments/alfworld-qwen2.5-1.5b-exact/run_metadata/dryrun_2gpu_seed1/local_2gpu_optimized_to_step_150/resolved_command.sh
```

当关闭里程碑保存时，结果应包含 `env.seed=1`、`main_reuse`、`root_active_executor=true`、`save_freq=5` 和 `max_actor_ckpt_to_keep=2`，且不包含 `milestone_checkpoint`。

### 4 卡 dry-run

```bash
cd /hpcwork/xsz96350/fu_project/work-BACE/verl-agent-src
DRY_RUN=1 GPU_COUNT=4 BACE_SEED=1 \
BACE_RUN_NAME=dryrun_4gpu_seed1 MILESTONE_CHECKPOINT_STEPS=none \
bash examples/bace_gigpo/run_alfworld_h100_4gpu_rolling.sbatch
```

4 卡 metadata 位于：

```text
experiments/alfworld-qwen2.5-1.5b-exact/run_metadata/<run_name>/local_rolling_to_step_150/
```

检查 `run_metadata.txt` 中的 `seed=1`、`GPU_COUNT=4` 和 `BACE_SEED=1`，以及 `hydra_overrides.txt` 中的 `main_reuse` 和 `root_active_executor=true`。

## 6. 运行期间查看状态和日志

```bash
# 查看指定作业状态与等待原因
squeue -j <job_id> -o '%.18i %.24j %.10P %.16a %.9T %.10M %.10l %.30R'

# 作业结束后确认 Slurm 退出码
sacct -j <job_id> --format=JobID,State,ExitCode,Elapsed,Start,End,AllocTRES

# 持续查看 Slurm 输出
tail -f /hpcwork/xsz96350/fu_project/work-BACE/experiments/alfworld-qwen2.5-1.5b-exact/slurm/bace15b_2g_ref-<job_id>.out
tail -f /hpcwork/xsz96350/fu_project/work-BACE/experiments/alfworld-qwen2.5-1.5b-exact/slurm/bace15b_main_roll-<job_id>.out
```

训练日志的稳定位置是：

```text
experiments/alfworld-qwen2.5-1.5b-exact/logs/<run_name>/<invocation_id>.log
```

关键日志字段包括：

```text
training/global_step
val/success_rate
bace/batch_erv_exact
bace/staged_root_batching_packed
bace/branch_selected_worker_execution
bace/branch_main_pool_reuse
bace/root_active_executor_enabled
bace/requested, bace/validated, bace/skipped
bace/replay_validation_seconds
```

正式 step 应满足 `bace/batch_erv_exact=1`、`bace/staged_root_batching_packed=1`，且 branch 请求要么通过 Replay 验证，要么以显式失败记录终止。优化版还应出现 `branch_main_pool_reuse=1` 和 `root_active_executor_enabled=1`。

## 7. 产物、checkpoint 与 trace 验收

对任一 `<run_name>`，主要目录如下：

| 内容 | 路径 |
|---|---|
| 普通 checkpoint | `checkpoints/<run_name>/` |
| 长期 checkpoint（仅启用时） | `preserved_checkpoints/<run_name>/` |
| BACE trace artifact | `bace_artifacts/<run_name>/step_XXXXXXXX/` |
| TensorBoard event | `tensorboard/<run_name>/` |
| metadata、源码 SHA-256、解析命令 | `run_metadata/<run_name>/<invocation>/` |
| trace 验证报告 | `trace_validation/<run_name>/` |

运行完成后可手动重跑 trace 验证：

```bash
source /home/xsz96350/miniforge3/etc/profile.d/conda.sh
conda activate /hpcwork/xsz96350/fu_project/verl-agent
cd /hpcwork/xsz96350/fu_project/work-BACE/verl-agent-src

python3 -m recipe.bace_gigpo.validate_trace \
  /hpcwork/xsz96350/fu_project/work-BACE/experiments/alfworld-qwen2.5-1.5b-exact/bace_artifacts/<run_name> \
  --output /hpcwork/xsz96350/fu_project/work-BACE/experiments/alfworld-qwen2.5-1.5b-exact/trace_validation/<run_name>/manual_final.json
```

请注意：一次训练即使已经到达 step 150，作业仍可能因**训练后全量 trace 校验**失败。例如历史 2 卡 seed 0 run 曾在训练、validation 和 checkpoint 都完成后，因一个较早 step 的 JSONL trace 被截断而得到 Slurm exit code 1。因此最终验收应同时检查 global step、最后 validation、普通 checkpoint、artifact `summary.json` 状态以及 trace 报告的 `ok=true`。

## 9. 推荐的多 seed 操作流程

1. 为每个 seed 指定唯一且含日期的 run name。
2. 先执行对应卡数的 dry-run，核对 seed、优化调度和 checkpoint 参数。
3. 多 seed 复现实验使用 `MILESTONE_CHECKPOINT_STEPS=none`，以普通轮转控制空间。
4. 使用 `squeue` 等待资源；作业启动后检查 preflight、GPU 拓扑和 `training/global_step:1`。
5. 结束后检查 `sacct`、最终 validation、trace 报告和 checkpoint；再把正式 event 目录加入 TensorBoard 对比。
6. 仅当需要长期审计、消融恢复或中间模型导出时，才启用 seed 0 的永久 checkpoint 列表。

这样可以在不改变 BACE 方法定义的前提下，获得可比较的 2 卡与 4 卡多随机种子结果，同时将 checkpoint 磁盘占用控制在可恢复的范围内。
